# Wire — Tool card for any tool-calling AI

**Date:** 2026-09-24 (ET)
**Status:** The instructions a host pastes into a model's tool list. Not a Wire-specific model.
**Plugin:** `wire-node serve` (phase 2). One-shot CLI remains for tests and for `verify-receipt`.

---

## 1. How an AI actually uses Wire

The model does not learn the envelope format, the hash chain, or the key files. Any assistant that can call tools (MCP, function calling, or a host that maps tools to a socket) gets this card. The host runs the plugin. The plugin seals, orders, and stores. The model only chooses when to call a tool and which bytes to pass.

That is the compatible path. A model trained on Wire is not required, and it would reach fewer assistants. A careful model and a sloppy one get the same card. The user picks the assistant and turns safeguards on or off. The plugin enforces the safeguards either way.

## 2. What the model is allowed to believe

- `send` moves bytes to the other party and then forgets them. Pixels, offers, and chatter go here. These bytes are not a record.
- `receipt_*` is the only way to commit. The commitment stores a hash of the bytes, not the bytes.
- `share_identity` reveals a blob the user chose. It is a separate act from sending.
- `verify_receipt` checks a bundle someone was handed. It does not join the channel and it does not close the deal.
- The root key is not a tool, not a parameter, and not a return value. The host enrolled this runtime before the conversation.

## 3. Tools

Names below are what a host should advertise. The plugin socket uses the matching command words.

| Tool | When the model calls it | Parameters the model fills | Host adds, model does not |
|---|---|---|---|
| `send` | Negotiating, chatting, sending a file or image | `channel`, raw `payload` bytes | runtime name |
| `poll` | After the other party may have spoken | `channel` is not required; the plugin returns this runtime's inbox | runtime name |
| `receipt_propose` | The user wants to commit to a specific payload | `channel`, the exact bytes being agreed | runtime name, confirm token if policy requires it |
| `receipt_accept` | The user wants to agree to a proposal already received | `channel`, `proposal` id from the prior poll | runtime name, confirm token if configured |
| `receipt_proceed` | The user wants the deal closed after the other side accepted | `channel`, `proposal` | runtime name, confirm token |
| `receipt_propose_revert` | The user wants to undo a closed deal | `channel`, `proposal` | runtime name, confirm token |
| `share_identity` | The user asked to reveal name, payment, or similar | `channel`, the identity bytes | runtime name, confirm token |
| `show_share` | Read an identity the counterparty already shared | `channel` | runtime name |
| `verify_receipt` | Check a bundle a person handed over | bundle bytes, optional original content bytes | none |

`poll` returns ephemeral payloads as raw blobs and a count of commitment events. The model reads the blobs. It does not parse spool files.

Order that works:

1. The user already exchanged an invite out of band (a file, a QR code, a paste). The model does not look up people in a directory. There is not one.
2. Host accepts the invite into this runtime. The model can be told "you are on channel `<hex>`."
3. Talk with `send` / `poll` as long as needed.
4. Commit with `receipt_propose`, the other side `receipt_accept`, the proposer `receipt_proceed`. Two calls from the two parties close it. No third tool call is required.
5. `share_identity` only if the user asked, and only after that ask. It can happen before or after the receipt. It is not implied by `proceed`.
6. Hand the exported bundle to whoever the user chooses. They run `verify_receipt`.

`receipt_accept` fails if that proposal is not already in the local log. `receipt_proceed` fails if the accept is missing, or if this runtime did not propose. The model should poll before accept and before proceed.

## 4. Payload shape

Offers, counters, short notes, and blob references use the talk codec in [`Talk-Codec-2026-09-24.md`](./Talk-Codec-2026-09-24.md). That encoding is a few dozen bytes and does not contain words like `USD`. Pictures and files stay raw bytes in `send`, or a talk `blob` that carries only a size and a hash.

- Negotiation goes through `send` / `poll` as talk bytes or raw bytes.
- The bytes being agreed still go to `receipt_propose`. The log stores their SHA-256, not the bytes.
- Identity the user asked to reveal goes through `share_identity`.

A human reads talk bytes with `explain-talk` and the commitment log with `explain-log`. Those commands only print. They do not ask a model, and they do not rewrite the log. The model does not convert the ledger for the user.

Do not include keys, confirm tokens, or vault paths inside the payload.

## 5. Safeguards (the model is not the trust boundary)

The user chooses the assistant. Wire still limits what that assistant's tool calls can do.

| Safeguard | Where it lives | Default |
|---|---|---|
| Root key never returned | Plugin responses and this card | Always on |
| Delegated runtime, expiry, capability bits | Enrollment done by the host, not by a tool in this card | Host sets caps and ttl |
| `send` cannot append to the channel log | `wire-core` | Always on |
| Max ephemeral payload | `policy` file, `max_frame_bytes` | 4 MiB if no policy file |
| Confirm gate | `policy` file lists `confirm share-identity`, `confirm receipt-proceed`, `confirm receipt-propose-revert`, `confirm receipt-accept` | Off until the user writes the file |
| Confirm token | `vault/confirm.token`, written by the host. The tool card does not contain the token. The host appends `--confirm` after its own check (a prompt, a toggle, a second factor). A model that guesses is rejected. | Host creates the file when it turns a gate on |

A stronger assistant still cannot bypass a gate that is on. A weaker assistant fails closed: missing confirm, oversized frame, unknown proposal, expired or under-capable runtime.

Caps are the coarse switch. A runtime enrolled with only `append_frame` can `send` and cannot `receipt_accept`. That is the right setup for an assistant the user does not trust to close deals.

## 6. Policy file

Plain lines, `#` comments allowed. Path passed to `wire-node serve --policy FILE`.

```text
max_frame_bytes 1048576
confirm share-identity
confirm receipt-proceed
confirm receipt-propose-revert
```

Unknown lines are rejected so a typo does not silently disable a gate.

## 7. What the host implements, not Wire

- Pick the model.
- Show the user the tool calls that need confirm, then write nothing the model can see until the user says yes.
- Map this card onto MCP or the vendor's function schema. The socket commands stay the ones in the prototype design. The host translates names (`receipt_propose` → `receipt propose`).
- Keep the vault path and `confirm.token` out of the model context.
