## 1. Thesis (what we are actually building)

**Product (Wire) = a secure, history-verifiable, massively scalable communication fabric for AIs.**

It is a means of communication between AIs: E2E encrypted delivery, per-channel append-only commitment logs, bilateral agreement receipts, privacy-first (blind until explicit share), local-first storage by default. Scale comes from many independent channels, not from one global ledger. Ephemeral traffic (offers, chatter, pixel streams) is delivered and dropped. Only interactions that must stay provable are persisted.

Wire is the fabric under the AIs, not the AIs themselves, not UX shells, and not an intent taxonomy. Intent type is opaque to this service. Payloads may be structured bytes today and pure binary or pixel streams tomorrow. The fabric carries opaque encrypted frames. The shared history is membership, receipts, and explicit shares.

**Why** (context only): personal AIs, personalized UX, cloud or on-device agents — those live *above* this layer. Any AI, anywhere (phone, laptop, datacenter, edge), should be able to speak this protocol.

Defaults: **privacy first**, **safety-capable**, **crypto-agile** (including post-quantum), **no single omniscient ledger**, **many independent identical-underneath channels**, groupable/mergeable with **selective disclosure** of PII.

## 2. What this is / is not

| Is | Is not |
|---|---|
| AI↔AI transport + commitment ledger + receipts | Hosting or running the AIs |

## 2b. Locked design decisions (2026-09-24)

| Decision | Lock |
|---|---|
| **Principal custody** | User-held **root** keys only. Runtimes (any AI/device) receive **short-lived delegated** keys via enrollment — never the root. Cloud vendors are untrusted for root custody. |
| **History claim** | Wire provides **per-replica evidence**: each party can prove what *they* signed and received. It does **not** claim a single global canonical channel history without additional sync rules (future / optional). |
| **Discovery v0** | **Out-of-band invite / capability URL only.** No public contact directory in v0. |
| **Receipts v1** | **Bilateral only.** Multi-party deals = compose multiple bilateral receipts. N-of-M receipts deferred. |
| **Relay in prototype** | **Yes — stub in scope.** Localhost (or in-process) store-and-forward so offline/NAT delivery is real, not fantasy. Relay is untrusted for confidentiality; sees metadata (threat model D). |
| **Compaction** | [`Compaction-Policy-2026-09-24.md`](./Compaction-Policy-2026-09-24.md): **unilateral local hot truncate** of the persisted log anytime; optional bilateral snapshot/ack = shared checkpoint only (not a truncate gate); **no silent channel-wide delete**; archive if *you* want to keep evidence. Ephemeral frames are never truncation candidates because they are not logged. |
| **Two planes** | **Ephemeral frames** (offers, chatter, pixels, any ordinary payload) are sealed, queued by the relay until ack or TTL, then dropped. They are not hash-chained. A local retain flag may keep a private copy; that copy is not the shared log. **Persisted events** are the only shared history: `member_add`, `member_cap_update`, `propose`, `accept`, `proceed`, `propose_revert`, `accept_revert`, `share_identity`, `snapshot`, `ack_snapshot`, `handle_rotate`, `cred_revoke`. |
| **Content hash** | A `propose` body stores `proposal_id` and a SHA-256 of the agreed bytes. The bytes stay off the log. |
| **Finality** | Two parties finish the deal. `propose` + `accept` + `proceed` on the same proposal hash is final between those principals. Consent policy lives in each AI's settings. Wire records the signed confirmation. No shipper, payment processor, or verifier is in that path. |
| **Offline verify** | A receipt bundle is exportable. A third party with the bundle and no channel membership can check both signatures and the content hash. Verification is not participation. Identity is in the bundle only if a `share_identity` event was included in the export. |
| **Scale bar** | Many independent deals over TCP. The prototype test is 8 nodes, 32 concurrent channels, ≥256 KiB ephemeral payload each, one persisted receipt trio. Pass means per-channel hot logs stay under 4 KiB, total ledger bytes stay under 32 × 4 KiB, there is no global log, non-members store nothing, the relay spool drains, and every receipt verifies offline. This is the scaling shape, not a production WAN claim. |
| **Client shape** | A local plugin/daemon (`wire-node` plus `wire-core` in this prototype). First run creates one principal vault and a contact handle if the path is empty, and refuses to overwrite an existing vault. Each AI on the device is a runtime enrolled with a short-lived delegated key. A second AI does not mint a second principal. The model never sees the root. An MCP adapter is later, over this same command surface. |

## 3. Answers to locked founder constraints

### 3.1 Quantum computing — does it change the one-pager?

**It changes crypto choices and agility requirements; it does not change the architecture.**

| Layer | Quantum impact | Future-proof move |
|---|---|---|
| Channel membership, signatures, key exchange | Shor breaks RSA/ECC; Grover weakens symmetric (~2× key length) | **Crypto agility**: algorithm IDs in envelopes; support **hybrid** classical + PQC (e.g. ML-KEM / ML-DSA class) from day one or as first upgrade path |
| Opaque payloads / binary / pixels | None (content-agnostic) | Keep payload opaque |
| Channel model, receipts, privacy-blind default | None | Unchanged |
| “Harvest now, decrypt later” | Real risk for long-lived encrypted logs | Prefer PQ-hybrid **for channel encryption keys** early; allow re-key / ratchet |

**Design rule:** never hard-code a single signature or KEM. Version the crypto suite. Plan migration the way TLS did cipher suites. It is *not* too early to put agility in the envelope format; it *is* too early to bet the product on speculative quantum networks.

Cousins: NIST PQC (ML-KEM, ML-DSA, SLH-DSA), hybrid TLS experiments, Signal/MLS crypto agility discussions, liboqs (evaluate carefully; prefer audited US/ally sources).

### 3.2 Scope: fabric only; opaque payloads; sub-AIs; any topology

- AIs and UX shells are **clients** of this system, not part of it.
- Intent type **does not matter** to the service — only envelope, membership, ordering, receipts.
- An interaction may start with 2 AIs and grow to **hundreds of sub-AIs** on the **same shared channel(s)** (membership + capability grants).
- Topology-agnostic: on-device ↔ on-device, cloud ↔ cloud, mixed. Location is irrelevant if keys and channel IDs work.
- Future vision (binary / pixel streams): **opaque ephemeral frames**. No schema enforcement in-core. Those frames are delivered, not appended. A commitment to a blob is a content hash inside a receipt.

### 3.3 Privacy pillar — blind until explicit share

- Default: parties communicate **without** mandatory identity, payment instruments, or other PII in the clear.
- Identifying fields transfer only on an **explicit share event** (AI may automate consent per user policy; the fabric still waits for that share event — it does not scrape or require early identity).
- **Channel merge / group:** merge policy must choose whether PII-bearing events are included, redacted, or left in a sealed side-log. Selective disclosure is a first-class merge option.

### 3.4 Massive scale + implementation language

- Hot path: create channel, deliver an ephemeral frame, append a commitment event, membership add — must be cheap, and must touch only that channel's state.
- **Preferred language: Rust** (memory safety, performance, strong AI-assisted maintainability without C++ footguns). C/C++/Zig only if a measured hot path demands it.
- “Not human-readable” is fine for wire format; **source should stay reviewable** for TDD and audits.
- Avoid premature “write it in assembly.” Profile first.

### 3.5 Local-first storage (configurable elevation)

- Default: each participant AI stores the channel ledger **locally**.
- Optional elevation to online/shared storage is **config** (relay, backup, org vault) — never required for the happy path.
- Sync is peer (and optional helper) driven, not “upload everything to our cloud.”

### 3.6 Three layers: principal ≠ runtime ≠ contact

Identity must survive **AI upgrades, switching AI vendors/models, and moving across devices**. The fabric treats these as separate concepts:

| Concept | Role |
|---|---|
| **Principal** (user-controlled long-lived identity) | Who the *party* is across time — keys the user owns; can be continued when they swap AIs or devices |
| **Runtime / AI instance** | The software currently speaking the protocol (Claude today, local model tomorrow, cloud later) — **replaceable**; not the durable identity |
| **Contact handle(s)** | How others *reach* the principal (multiple allowed; rotatable after spam/leak — “change your number”) |
| **Voluntary new identity** | User may mint a fresh principal anytime (persona, clean start) — choosing continuity is optional, not forced |
| **Per-interaction addresses** | Optional for high-sensitivity threads; **not** the default for ongoing relationships |

**Continuity mechanism (locked):** root principal keys stay in **user-held** storage; new runtimes are **enrolled** and receive **short-lived delegated** keys only (never the root). History, channels, and handles stay bound to the principal across AI/device swaps without trusting cloud vendors with root custody.

Unlike Bitcoin’s “new address every payment” social default: ongoing relationships need stable reachability *and* easy rotation of the public contact surface — while still allowing a deliberate identity reset.

### 3.7 Bilateral agreement receipts (finality between two AIs)

- Service does **not** care how AIs decide.
- Service **does** require a clear receipt pattern: e.g. `propose` → `accept` (both signed) → `proceed` / later `propose_revert` → `accept_revert`.
- Two different AIs can “agree” by producing matching signed accepts bound to the same proposal hash. That is the confidence layer.
- **v1 scope:** bilateral receipts only; multi-party = compose multiple bilateral pairs.

### 3.8 Engineering standards

- **Test-driven**, thorough E2E (multi-process, multi-member, merge, rotate handle, privacy share, revert agreement).
- **Minimize third-party deps**; do not reinvent audited crypto primitives.
- Prefer **US or close-ally** maintained deps; vet each for overhead vs writing a thin internal piece.
- Be **more confident in own design** before rejecting a dependency — measure and justify.

### 3.9 Retention: append-only; reversible by agreement (not “coins gone forever”)

- Default: **add-only** ledger; no silent deletes.
- Users may discard or stop sharing a local copy; that is their choice.
- Avoid crypto-wallet-style irreversible footguns: wrong-destination permanence is **not** the model.
- **Compensating / revert events** agreed by parties are first-class (history preserved; semantic undo via new signed events).

### 3.10 Git / association

- Work under **TheFuturist** git account only for now.
- Do not brand as AG or Sale Spotted; personal/company association deferred.

## 4. Architecture (revised)

```
┌──────────────────────────────────────────────────────────┐
│  ANY AI runtime (device / cloud / edge) — OUT OF SCOPE   │
│  UX shells — OUT OF SCOPE                                │
├──────────────────────────────────────────────────────────┤
│  Principal · runtime enrollment · contact handles (rot.) │
├──────────────────────────────────────────────────────────┤
│  Wire — channel fabric (this product)                    │
│    • ephemeral encrypted frames (not logged)             │
│    • append-only signed commitment log per channel       │
│    • membership (incl. sub-AI spawn / grants)            │
│    • bilateral receipts; two-party finality              │
│    • exportable receipt a third party can verify         │
│    • privacy: blind until explicit share events          │
├──────────────────────────────────────────────────────────┤
│  Plugin ports (config-swappable)                         │
│    identity · network correlators (e.g. IP) ·            │
│    attestation · public anchor / finality provider ·     │
│    storage elevation · crypto suite                      │
└──────────────────────────────────────────────────────────┘
```

### 4.1 Channels & scale

- Channel ≈ independent ledger of **commitment** events (identical rules underneath).
- Ephemeral frames are a delivery queue, partitioned by recipient, deleted on ack. They are not a second ledger.
- Create / append / member-add must be O(small) local work on that channel only; avoid global consensus per event.
- Grouping = indexes over channel IDs; merging = policy-controlled inclusion (incl. PII filter).
- The prototype scale test (8×32, large ephemeral payload, tiny logs) is the check that this stayed true.

### 4.2 Interaction / network identity

- Always: Channel ID, Event ID, signer key IDs.
- Optional correlators: IP/ASN/etc. as **hints** for abuse/ops — not required identity.
- PII only after explicit share events.

### 4.3 Crypto agility (quantum-ready posture)

Envelope fields include `suite_id`. Initial target: modern classical + documented upgrade path to **hybrid PQC**. Ratcheting / re-key supported so long-lived local ledgers can upgrade confidentiality.

## 6. Two-week prototype (revised)

**In-scope:**
1. Rust workspace: channel create, local append-only **commitment** log, multi-process E2E over TCP.
2. Ephemeral opaque frames + crypto envelope with `suite_id` (classical suite 1; suite 2 stub rejected for seal/sign). Frames are not appended.
3. Membership: add a sub-participant with reduced caps to one channel.
4. Bilateral receipts: propose/accept/proceed + propose_revert/accept_revert. Finality is the two signatures. `verify-receipt` checks an export with no relay and no membership.
5. Privacy: channel works with keys alone; explicit `share_identity` event optional and persisted.
6. Contact layer: one vault, many delegated runtimes; rotate one handle; mint to the old handle fails; root never signs events.
7. Storage: per-channel directories only. Local retain flag writes a private side file, not the log.
8. Merge stub: export with `include_pii: false|true`.
9. **Relay stub:** TCP store-and-forward; deliver when the peer was offline; delete ephemeral spool on ack. Relay sees routing metadata, not plaintext.
10. **Compaction stub:** unilateral local hot truncate of persisted events; archive re-verifies a receipt; peer replica unaffected. No snapshot required to truncate.
11. **Scale test:** 8 processes, 32 channels, ≥256 KiB ephemeral payload, receipt trio only on the log.
12. TDD + E2E; deps limited to audited crypto ([`DEPS.md`](./DEPS.md)).
13. Fork detection: two replicas diverge → report conflict (no silent auto-merge). Truncate still allowed locally.

**Out-of-scope:** AI runtimes, UX shells, MCP adapter, intent registries, AG watermark, real multi-L1 consensus, production multi-tenant relays, automatic global canonicalization, logging ephemeral media.

**Success:** Many processes complete encrypted ephemeral exchange via the relay (including offline delivery) without those bytes entering any channel log, close a deal with two signatures, let a non-member verify the export, spawn a capped sub-member, rotate a contact handle, selectively merge without leaking PII when configured, detect a fork, unilaterally compact one replica’s hot log while still verifying from archive, and pass the 8×32 scale assertions.

## 9. Adversarial hole-poke (2026-09-24) — before prototype

Intentional stress test. Severity: **Blocker** (must decide or accept risk) → **Hard** (design now or prototype will lie) → **Watch** (defer but don't forget).

### Blockers

**B1. Bootstrap / discovery without a surveillance directory**  
Contact handles must resolve somehow. A public directory is a spam + metadata honeypot; pure peer discovery fails for strangers and offline AIs. *Decide:* sealed introduction (in-person/QR/out-of-band), invite-capability URLs, optional private directory, or hybrid — and what metadata relays may see.

**B2. Principal custody vs cloud/vendor AIs**  
“User-controlled principal across AI swaps” collides with hosted runtimes that will not hold your root keys. If the principal lives inside OpenAI/Anthropic/xAI/etc., continuity becomes **vendor lock-in again**. *Decide:* principal always offline/on-device (runtime gets short-lived delegated keys only), or accept weaker “continuity” for cloud-only users.

**B3. Local forks vs “history-verifiable”**  
Append-only local logs + no global consensus ⇒ two honest parties can disagree after partition, selective sync, or malice. Verifiable *to a replica* ≠ shared truth. *Decide:* what Wire claims — “each party can prove what *they* signed and received” (honest) vs “the channel has one canonical history” (needs stronger sync/consensus rules).

**B4. Revert-by-agreement fails when you need it most**  
If one side refuses to `accept_revert`, you’re stuck — exactly the fraud/dispute case. Avoiding crypto’s irreversible footgun is good; pretending dual-consent undo replaces dispute resolution is not. *Decide:* Wire stops at dual-consent receipts (document the gap), or add optional escrow/arbiter/plugin later — but don’t market “reversible” as magic.

### Hard design choices (prototype will fake these if skipped)

**H1. Blind start vs linkable cryptographic identity**  
Ephemeral peer keys are still pseudonyms. Traffic patterns, channel graphs, and long-lived principals deanonymize. “Privacy first / blind until share” needs a precise threat model (against peer? against relay? against global passive?). Sealed-sender-class metadata protection is hard at scale.

**H2. Hundreds of sub-AIs on one channel**  
Membership churn, revocation, and a compromised sub-AI still matter. Ordinary chatter and pixel streams are ephemeral, so they do not grow the hash chain. The persisted log is commitments only. *Still need:* roles/capabilities, fan-out limits, child channels for high-churn **commitment** work, compaction of that log (without silent delete). The scale test checks many channels, not hundreds of members on one channel.

**H3. Multi-party deals ≠ bilateral receipts**  
Buyer ↔ seller is 2; real commerce often needs payment rail / shipper / platform. Bilateral `propose/accept` doesn’t compose cleanly to N-of-M. *Decide:* v1 is strictly bilateral (compose multiple bilateral receipts), or design multi-party receipt early.

**H4. Relays are optional on paper, mandatory in practice**  
Phones, NATs, sleep, and cloud↔device need store-and-forward. Relays learn timing, sizes, and graph edges even if payloads are E2E. Elevate relay threat model to first-class; “optional helper” underplays it.

**H5. Append-only vs erase/compliance**  
Peers keep copies; “user deletes local ledger” doesn’t erase the other side. GDPR-style erasure and “no silent delete” conflict. *Decide:* Wire’s stance (crypto-honest retention + legal process outside protocol vs sealed/expiring ciphertext with timed key destruction).

**H6. Selective PII on merge is crypto-awkward**  
You can’t truly redact from a hash-linked append-only log without breaking verification or keeping ciphertext forever. Merge `include_pii: false` may mean “omit events / share sealed blobs with separate keys,” not magic redaction. Prototype must not pretend ciphertext vanishes.

**H7. Raw transport is not the win**  
HTTPS already moves opaque bytes. Wire’s win is two-party receipts, membership, a local commitment history, ephemeral delivery that is not retained, and offline sync. Market those properties.

**H8. Safety-capable vs opaque payloads**  
If Wire cannot inspect content, safety is client policy + abuse at the envelope layer (rate limits, member bans). Claiming fabric-level safety without inspection overpromises. Keep safety as **capability hooks + client responsibility**.

**H9. Adoption / chicken-and-egg**  
No AI ships Wire clients yet. Labs are pushing A2A/MCP/agent RPC. Risk: a protocol with zero callers. The client shape is a **local plugin/daemon** any tool-using AI can call: one vault per person, delegated keys per runtime, commands for ephemeral send, receipt, share, and offline verify. The prototype ships the library and CLI that adapter will wrap. It does not claim labs already integrate it.

**H10. Name collision**  
Wire (chat), WireGuard, wire transfer. Fine as internal codename; check trademarks before public brand.
